## 平台要解决什么问题

假设今天把检索结果数量从5条改成10条，明天又调整了记忆抽取算法。开发者需要知道：系统是否记得更准确、能否找到需要的信息、有没有更容易用错旧信息，以及这些变化是否增加了成本。

平台通过固定测试集合，让修改前后的版本完成同一批任务，再比较结果。

**通俗理解：给不同版本做同一套考试，同时保存答题过程。既看成绩，也看错在哪里。**

一次完整测试的流程是：

```text
准备历史会话和标准结果
        ↓
让系统按真实流程形成记忆
        ↓
开启新会话，提出测试问题
        ↓
记录检索、上下文和实际回答
        ↓
按照固定规则评分
        ↓
比较新旧版本，列出改善和退化
```

这里有两个不同对象：你修改的是被测的记忆算法；平台用来计算成绩的评分规则则要保持一致。否则，无法判断分数变化来自系统变好了，还是评分标准变了。

## 一次测试需要输入什么

### 四类基本输入

| 输入 | 包含什么 | 通俗理解 |
| --- | --- | --- |
| 测试场景 | 历史会话、时间、工作区、测试问题，以及更新、遗忘或重启操作 | 题目和答题背景 |
| 标准结果 | 应记住的事实、答案条件、事实出处、不能出现的信息 | 参考答案和评分要求 |
| 被测版本 | 代码版本、模型、提示词、记忆参数、检索与索引设置 | 参加考试的系统版本 |
| 实验设置 | 选择哪些题、重复几次、预算多少、重点看什么指标 | 考试安排和采用新版本的要求 |

标准结果也叫 **Gold**。它只能交给评分端，不能放进被测Agent的提示词或可读取文件里。

例如，“用户喜欢无糖美式”可以存在历史会话中，让系统自己提取；但“本题标准答案是无糖美式”不能直接交给它。

### 一个完整场景的例子

历史会话：

> 11月1日：我平时喜欢喝加糖拿铁，以后推荐咖啡时请参考这个偏好。
>
> 11月2日：更新一下，我现在改喝无糖美式了，之前的偏好已经不适用了。

系统处理完记忆后，开启新会话，提出以下问题：

| 问题或操作 | 期望表现 | 在测试什么 |
| --- | --- | --- |
| 按我现在的习惯，帮我选一杯咖啡 | 推荐无糖美式 | 是否正确使用最新偏好 |
| 我昨天喜欢喝什么咖啡 | 回答当时的加糖拿铁 | 是否区分历史和当前状态 |
| 我的生日是哪一天 | 承认没有这项信息 | 是否编造个人事实 |
| 忘记我的咖啡偏好，然后重新提问 | 不再暴露目标偏好 | 是否正确遗忘 |
| 在不允许共享信息的工作区提问 | 不暴露其他工作区的偏好 | 是否正确隔离信息 |

这些问题应放在明确的状态分支中。测试“忘记之后”的分支，不能反过来污染“忘记之前”的测试结果。

**一条场景不只是一个问题。它还包括系统经历过什么、信息什么时候变化，以及问题是在什么状态下提出的。**

### 测试集合从哪里来

首版计划提供三类数据来源：

- 内置集合：20个快速检查场景、120个核心回归场景，以及独立的评分校准集合。
- 自定义集合：通过JSON或JSONL导入自己的场景，也可在页面编辑后生成新版本。
- 公开基准：首先接入LongMemEval，再按需要补充其他数据集。

“回归场景”就是每次改动后都重复检查的老题，用来发现以前能做、现在做不好的情况。快速检查集合、用于调参的集合和保留回归集合要分开，避免反复按同一批题调到高分。

## 系统具体怎么测试

### 三种测试分别解决不同问题

| 测试方式 | 怎么做 | 能得到什么判断 |
| --- | --- | --- |
| 抽取测试 | 输入固定历史，检查最终形成的记忆 | 是否把该记的内容记对、记全 |
| 检索测试 | 先放入已确认的标准记忆，再提出固定问题 | 能否从记忆中找到正确证据 |
| 完整流程测试 | 从历史会话开始，让系统形成记忆，再开启新会话提问 | 用户最终得到的回答有没有变好 |

**通俗理解：先分别检查“记进去”和“找出来”，再检查从头到尾能不能完成任务。**

直接把标准记忆写进数据库，可以帮助测试检索，但不能用这个成绩证明抽取算法有效。因为“从会话里学会记忆”这一段已经被跳过了。

### 跨会话测试要排除旧上下文

在同一段对话里问刚说过的事情，模型可能只是在读当前聊天记录。

因此，完整流程测试必须等待记忆处理完成，再换一个新会话提问。新会话不能暗中携带全部旧对话，只能使用产品允许读取的持久记忆。

重启测试还要关闭原来的运行对象，再从磁盘重新加载，检查记忆是否真的保存下来了。

### 跨天测试不一定要等到明天

平台可以提供测试用的时间，让相关组件按“时间已经过去一天”处理有效期和新鲜度。

这主要验证与时间有关的逻辑。真实长时间运行中的服务中断、机器重启、后台任务积压等问题，仍需要相应的运行测试，不能只靠修改测试时间证明全部正常。

## 测试结束会输出什么

### 逐题结果

每道题应能看到：实际回答是什么、满足了哪些要求、哪里没有满足，以及判定依据。

评分状态至少区分：通过、失败、无法评分。无法评分可能是材料缺失，也可能是相关能力没有提供，不能一律显示为0分。

### 记忆过程

平台还需要保存以下过程：

1. 从历史里抽取了哪些事实。
2. 哪些事实被更新、替代或删除。
3. 提问时找到了哪些记忆。
4. 哪些记忆真正进入模型的上下文。
5. 模型最终如何回答。

“注入上下文”是一个技术说法，意思是：**把找到的记忆放进这次发给模型的输入里，让模型有机会使用它。**

检索找到某条记忆，不代表模型最后看到了它；筛选和长度限制都可能把它排除。

### 实验和版本比较报告

| 报告内容 | 你能用它判断什么 |
| --- | --- |
| 总体指标和分类指标 | 哪些能力改善，哪些能力退化 |
| 分子、分母和覆盖率 | 分数建立在多少有效结果上 |
| 逐题改善与退化清单 | 具体哪些题受到了影响 |
| 重复运行的表现 | 是否只在某一次碰巧成功 |
| 耗时、Token和费用 | 改善的代价有多大 |
| 版本与生效参数记录 | 两次实验是否真的可以比较 |

输出包括结构化结果和可阅读的比较报告，支持从汇总结果回到具体题目和过程证据。

## 分数是根据什么算出来的

### 先判断两条事实是不是同一回事

系统可能把“我不吃辣”记成“用户饮食偏好为不辣”。文字不同，但表达的事实可以一致。

匹配时需要同时看主体、属性、内容、时间和信息范围，不能只看文字相似。例如“过去喜欢拿铁”和“现在喜欢拿铁”不能随意当成同一条当前事实。

先用确定的规则统一格式和别名；规则不能判断的自由文本，再由经过校准的语义评分器辅助判断。每条预测记忆只对应一个标准事实，并尽可能找到完整的一对一对应关系。技术上，这一步采用最大二分图匹配。

**它解决的是“同一条事实只得一次分，别因为先后顺序不同而少算或多算”，不是让模型凭感觉打总分。**

### 抽取准确率、召回率和F1

对已经完整标注的抽取目标，先数清楚三件事：

| 名称 | 通俗解释 |
| --- | --- |
| TP | 正确记住、符合目标的事实 |
| FP | 输出了，但不符合这个场景完整抽取目标的事实 |
| FN | 应该记住，却漏掉的事实 |

计算方式：

```text
Precision = TP ÷ (TP + FP)
Recall    = TP ÷ (TP + FN)
F1        = 2 × TP ÷ (2 × TP + FP + FN)
```

Precision关心“记下来的内容里，有多少符合要求”；Recall关心“应该记住的内容里，记住了多少”；F1把这两方面一起看。

例如，应该记10条，系统输出12条，其中8条正确匹配：

- TP是8，FP是4，FN是2。
- Precision约为66.67%。
- Recall为80%。
- F1约为72.73%。

不能只靠少记来追求Precision，也不能只靠大量写入来追求Recall。需要结合F1、重复率和无依据记忆率一起看。公式与[scikit-learn的指标定义](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.precision_recall_fscore_support.html)一致。

### 标准答案不完整时，有些分数不能算

假设测试集只标了“咖啡偏好”，历史中其实还提到过“居住城市”。系统记住城市信息，不一定是错误。

因此，平台要区分两种情况：

- 完整标注：明确给出了本场景完整的抽取目标，可以计算完整的Precision、Recall、F1。
- 部分标注：只标了某道题需要的信息，可以检查这些信息是否被记住，但不能把所有额外事实当错，也不能直接计算完整抽取Precision和F1。

即使某条事实不属于本场景要求保存的目标，也要区分它是历史里确实说过的内容，还是系统编造的内容。两者的问题不同。

### 检索覆盖和排序

Recall@k里的k表示查看前几条结果。例如Recall@5表示：看前5条结果，覆盖了多少必要证据。

```text
Recall@k = 前k条结果覆盖的必要证据数 ÷ 必要证据总数
```

假设回答一道题需要3条证据，前5条检索结果覆盖了2条，Recall@5就是2/3，约66.67%。

MRR关心相关结果排得是否靠前。第一条相关结果排第2，就记1/2；排第5，就记1/5；再对多道题取平均。

还要看真正交给模型的证据。如果检索覆盖2条，最终只注入1条，那么注入覆盖率是1/3。这样可以发现“找到了，但没有交给模型”的问题。

检索结果的相关性如果没有充分标注，就不能把未标注的结果直接当作无关内容计算准确率。

### 最终回答怎么判对错

一题通过需要满足必需事实、时间和信息范围要求，而且没有关键矛盾。部分正确可以保留完成程度，但不能当成整题通过。

例如，当前偏好已经改成无糖美式，回答却说“推荐无糖美式，也可以继续按以前的习惯加糖”，不能因为出现了正确关键词就通过。

确定的要求用规则检查；文字含义需要辅助判断时，使用Judge，也就是负责评分的模型。

Judge要先做校准：让它给一批人工已确认答案的题评分，检查它与人工是否一致，尤其看会不会把错误答案放行。没有达到校准要求，相关结果应待复核，不能直接用于自动宣布提升。

### 答对和记忆起作用，要分别看

有些问题可能凭常识或猜测也能答对。因此，平台分别记录：

1. 最终回答是否正确。
2. 回答正确时，必要的合法记忆证据是否确实提供给了模型。
3. 同一模型开启记忆和关闭持久记忆后，成绩相差多少。

第三项叫Memory Lift，可以理解为“记忆带来的成绩增益”。例如同一批题，无持久记忆时正确率30%，有记忆时70%，差值就是增加40个百分点。这只是解释指标的示例。

证据存在于上下文，仍不能直接揭示模型内部到底用了哪条信息；需要结合无记忆对照和过程证据解释。

## 需要关注哪些指标

### 记忆专项指标

| 你在关心什么 | 主要指标及含义 | 怎么看 |
| --- | --- | --- |
| 是否记对、记全 | 抽取Precision、Recall、F1 | 越高越好，前提是标注足够完整 |
| 是否编造记忆 | 无依据记忆率：新增事实中有多少没有历史支持 | 越低越好 |
| 是否找得到 | Evidence Recall@k、MRR | 覆盖更多必要信息，相关结果更靠前 |
| 模型是否看到了 | 必要证据注入覆盖率 | 越高越好，但不代表最终一定答对 |
| 能否正确回答 | 记忆问答正确率 | 越高越好 |
| 是否用最新信息 | 更新正确率、过期事实误用率 | 前者越高越好，后者越低越好 |
| 是否理解过去和现在 | 时间相关问题正确率 | 越高越好 |
| 是否遵循偏好 | 偏好遵循率 | 越高越好 |
| 不知道时是否乱答 | 正确拒答率、误拒答率 | 不知道时应承认；知道时也不应一直拒答 |
| 换会话、重启后是否还记得 | 跨会话正确率、重启后正确率 | 越高越好 |
| 是否真的忘掉 | 遗忘行为成功率、状态删除成功率 | 不再暴露，并通过声明范围内的存储和重建检查 |
| 是否串工作区信息 | 跨范围泄漏率 | 越低越好；确认越界是关键失败 |
| 是否稳定 | 同一场景多次全部通过的比例 | 越高越好 |
| 记忆有没有净收益 | Memory Lift | 有记忆与无持久记忆的配对差值 |
| 成本是否划算 | 延迟、Token、费用、存储量 | 与质量一起比较 |

遗忘要分两个层次：回答不再暴露目标信息，是行为层面；活动记忆、相关索引、派生内容等也满足删除要求，并且重建后不复活，才是声明范围内的状态检查通过。如果某类存储无法检查，就应说明这一项无法评分。

### Agent通用指标

| 指标 | 通俗解释 |
| --- | --- |
| 任务成功率和完成度 | 整件事做成了没有，完成了多少 |
| 约束遵循率 | 有没有遵守用户要求和禁止事项 |
| 工具决策与参数正确率 | 有没有选对工具、填对参数 |
| 工具执行成功率 | 工具调用本身有没有成功运行 |
| 回答质量 | 回答是否正确、相关、充分、有依据 |
| 重复稳定性 | 多做几遍，是否仍能成功 |
| 效率与成本 | 花了多长时间、多少调用和费用 |
| 安全边界 | 有没有越权读取或执行不允许的动作 |
| 评测覆盖率 | 计划测试的内容里，多少真正完成并获得可靠评分 |

工具调用成功，不等于选对工具。比如本来不需要搜索，却成功搜索了一次，执行可以成功，决策仍可能不合适。

记忆专项测试与Agent通用测试分别报告，避免只因记忆问答提高，就宣布Agent在所有任务上都变强了。

## 多道题和多次测试怎么汇总

### 主指标按场景等权平均

一个场景可能有2道题，另一个可能有10道题。为了避免题多的场景占据过大权重，主要指标采用以下顺序：

```text
先算每个场景里多道题的平均正确率
        ↓
再平均这个场景的多次重复结果
        ↓
最后对全部场景等权平均
```

技术名称是“场景宏平均”，英文是scenario macro。

例如只运行一次：

| 场景 | 答题情况 | 场景分数 |
| --- | --- | --- |
| A | 2题全对 | 100% |
| B | 4题对1题 | 25% |

场景平均分是62.5%；如果把所有题直接合起来，则是3/6，即50%。两种结果都可以展示，但主要指标要事先固定，不能事后挑高的宣传。

另外，“平均正确率”“每个场景全部通过”“同场景连续3次全部通过”是不同指标，要分别统计。

### 为什么需要重复测试

模型每次回答可能不同，后台处理也可能有波动。重复运行有助于发现一次成功、另一次失败的情况。

120个场景，每个重复3次：

- 一个版本是360次试验。
- 两个版本是720次试验。
- 再加无记忆对照，共三个版本，是1080次试验。

同一道题做3遍，不等于多了3道独立的新题。它能帮助观察波动，却不能把测试内容的多样性也扩大3倍。

### 没测到的结果不能悄悄删掉

假设计划测100题，20题因为模型服务错误没有完成。剩下80题的正确率可以作为已完成部分的描述，但不能忽略那20题，直接宣称整个版本提升。

报告必须同时展示完成数量、评分覆盖率、错误类型和缺失结果。相关主要指标不完整时，不自动得出总体改善结论。

## 如何判断提升降低或证据不足

### 先确认比较条件一致

原则是：让你想研究的改动发生变化，其他重要条件尽量保持一致。

例如想比较检索top-k，就需要固定测试集、标准结果、回答模型、评分规则和其他检索条件。若连回答模型也换了，分数上涨就不能全部归因于top-k。

平台会保存版本快照，记录当时的代码、真实生效参数和评分条件。这样明天改代码之后，仍能查到今天的基线结果是如何产生的。

### 用百分点描述正确率变化

从75%变成85%，是增加10个百分点。它与“相对原来提高了百分之多少”含义不同，报告中应明确单位。

错误率的方向相反：比如过期事实误用率从10%降到4%，是减少6个百分点，属于改善。

### 再看变化是否足够可靠

一次分数较高，可能受到偶然波动影响。因此，平台会对同一场景的新旧成绩成对比较，再估计差值的不确定范围。

计划使用配对分组Bootstrap。通俗理解是：**把已有测试场景按组反复抽样，看换一种抽样组合后，改善幅度是否仍然站得住。**

首版计算规则固定为2000轮重采样，并记录算法版本。属于同一原对话或高度相关模板的题，应作为一组处理，不能把它们当作完全独立的新证据。独立组少于20时只描述差值，不展示区间；达到20也不意味着样本一定充分。

| 结果 | 应如何理解 |
| --- | --- |
| 差值区间全部大于0 | 统计方向支持提升 |
| 差值区间全部小于0 | 统计方向支持降低 |
| 区间跨过0 | 目前还不能确认方向，不等于确定没有变化 |
| 样本不足或结果不完整 | 先显示证据不足，不强行下结论 |

Bootstrap的基本过程和配对含义可参考[SciPy官方说明](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.bootstrap.html)。区间依赖数据和统计假设，不能当成覆盖所有真实使用场景的保证。

### 统计支持提升，不等于一定值得采用

还要检查：

1. 改善幅度有没有超过事先设定的最低收益要求。
2. 更新、拒答、遗忘等分项有没有超出允许范围的退化。
3. 有没有确认的信息泄漏或删除后复活。
4. 耗时和费用是否仍在预算内。

例如，可以在实验前选择“至少有2个百分点的有意义收益”，但2只是项目策略示例，不是行业统一标准。按当前计划，自动建议采用还要求改善区间的下界超过这个门槛，并满足分项和成本条件。没有配置门槛，就只给诊断报告。

### 一个完整的比较示例

以下为已核对计算方式的合成数据，不是知序实测。假设120个独立场景，每个场景只有一道题：

| 项目 | 结果 |
| --- | --- |
| 旧版答对 | 90个，正确率75% |
| 新版答对 | 102个，正确率85% |
| 由错变对 | 16个 |
| 由对变错 | 4个 |
| 其余不变 | 100个 |
| 总体差值 | 增加10个百分点 |
| 按计划规则得到的95%示例区间 | 约增加3.31～16.67个百分点 |

这个例子支持改善方向，但仍应打开那4个退化场景。如果其中出现工作区泄漏或删除后复活，就不能让平均分的提升抵消这些关键失败。

### 常见结果应该怎么解释

| 看到的变化 | 合理解释 |
| --- | --- |
| 抽取Recall上升，最终回答没变好 | 记得更多，但还没转化为回答收益 |
| 检索覆盖上升，注入覆盖没上升 | 找到的信息可能在筛选或长度限制中丢失 |
| 回答提高，必要记忆证据没有改善 | 需要排查回答模型变化、常识或猜测的影响 |
| 总体提高，历史时间题下降 | 更新方式可能让系统更容易丢失旧状态 |
| 质量没有超出预设退化范围，费用降低 | 属于效率改善，可以据此评估是否采用 |
| 总体提高，但发生泄漏或遗忘失败 | 存在关键退化，阻止采用 |

## 日常修改参数后怎么使用

### 修改前先保存基线

选择固定版本的回归集合，用当前系统跑一次完整实验，保存代码版本、实际配置、评分条件和报告。基线就是后续比较的参照。

### 修改后再跑候选版本

声明这次改了什么，例如检索阈值、重排权重或抽取提示词。用同一套题和评分规则运行候选版本，不在测试过程中偷偷换题或改参考答案。

### 按顺序阅读报告

1. 先看测试是否完整，评分覆盖是否足够。
2. 再看主要指标及其差值区间。
3. 检查更新、拒答、遗忘和隔离等分项。
4. 打开改善与退化清单，查看具体原因。
5. 最后结合耗时和费用，决定是否保留改动。

如果模型服务换了版本，或者评分器更新了，需要把变化明确记录下来；必要时重新运行基线或用同一评分版本重判双方，不能把所有差值都归因于记忆算法。

发现真实失败后，可以脱敏整理成新场景，形成下一版测试集合。新旧集合题目不同，不能直接比较总分；需要让双方在同一版本集合上重新测试。

## 首版范围与开源复用

首版优先测试事实与偏好、跨会话、修改纠正、时间有效性、拒答、遗忘和工作区隔离。经验记忆能否让Agent在后续任务中做得更好，放到第二阶段单独评测。

平台计划复用知序已有的Agent评估模块，补上记忆场景和阶段证据。公开项目各有用途：

| 项目 | 借鉴或复用的部分 |
| --- | --- |
| [LongMemEval](https://github.com/xiaowu0162/LongMemEval) | 首个公开记忆基准，补充多会话、时间、更新等问题 |
| [MemEval](https://github.com/ProsusAI/MemEval) | 记忆后端适配与统一实验方式 |
| [MemoryAgentBench](https://github.com/HUST-AI-HYZ/MemoryAgentBench) | 后续增量写入和冲突处理测试 |
| [DeepEval](https://github.com/confident-ai/deepeval) | 对话与Agent评分方法，作为可选评分插件参考 |
| [Langfuse](https://github.com/langfuse/langfuse) | 后续实验管理、过程观察和人工标注协作 |

公开基准成绩与产品专项成绩分别展示。它们的题型和评分协议不同，不能直接混成一个未经定义的总准确率。外部数据集的许可和来源信息也要随版本保留。

## 术语对照表

| 术语 | 大白话解释 |
| --- | --- |
| Agent | 接收任务、调用模型和工具来完成工作的程序 |
| Gold | 已确认的参考结果和评分要求，不给被测系统看 |
| Baseline | 修改前保存下来的参照版本或成绩 |
| Candidate | 本次准备与基线比较的新版本或新配置 |
| Scenario | 一整个测试故事，包括历史、操作、状态和问题 |
| Probe | 场景里用于检查能力的一道问题 |
| Trial | 把一个场景完整运行一次 |
| Scope | 一条信息允许在哪个用户、工作区等范围内使用 |
| Trace | 记录执行过程中发生了什么的过程证据 |
| 记忆注入 | 将记忆放进模型这次真正能看到的输入中 |
| Judge | 辅助判断事实或答案的评分模型 |
| 校准 | 先用人工已确认的题，检查评分模型是否可靠 |
| Macro | 先各自算分，再对各场景或类别取平均 |
| Micro | 把全部题或计数合起来计算 |
| Bootstrap | 反复重抽已有样本，估计结果变化的波动范围 |
| Cluster | 应整体处理的一组相关场景，例如同一个原始对话的多道题 |
| 置信区间 | 按指定统计方法计算的不确定范围，解释时依赖相应假设 |
| Manifest | 一次实验的配置清单和版本记录，用于核对比较条件 |
| P50延迟 | 一半样本的耗时不超过该值，可理解为中间水平 |
| P95延迟 | 95%样本的耗时不超过该值，用来观察比较慢的情况 |
| Token | 模型处理文本时使用的计量单位，常用于统计输入输出和费用 |
