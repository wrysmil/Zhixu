# 知序记忆系统实操：40 题标注集与测试指南

## 1. 目标与交付

目标：能亲手观察“聊天内容写入长期记忆 → 换新会话检索 → 回答正确使用”，并在失败时区分写入、检索、回答三个环节。数据全部虚构，不需要输入真实个人资料。

本次交付是**评测设计与数据初稿**，没有改业务代码，没有启动网关、调用真实模型、改动真实用户记忆，也没有产出模型效果分数。

文件：

- 本指南：能力调研、完整题表、操作步骤、计分和归因规则。
- 历史语料与事实标注：`../research/2026-11-01-memory-eval/corpus.json`。
- 40 道逐题标注：`../research/2026-11-01-memory-eval/cases.jsonl`。
- 核查记录：`../verifications/2026-11-01-memory-eval-verification-lite.md`。

这是人工设计、尚未经过第二名标注员复核的合成集。不能称为“真实用户标注集”或“人工双人标注金标”。

## 2. 当前项目实际具备的能力

以下是代码证据，不等于已经测出的真实模型质量。核查基线为 `feature/desktop-app@ce595d6`。

| 能力 | 当前实现证据 | 应如何测试 |
| --- | --- | --- |
| 当前任务工作记忆 | `nanobot/agent/hooks/memory_extraction.py` 的 T0、`nanobot/agent/loop.py::_compute_working_memory_section` | 当前焦点与话题变化；不能用同一会话答对来证明长期记忆 |
| 语义记忆：身份、偏好、规则、技能、错误、经验 | `nanobot/memory/models.py::MemoryType`、`prompts.py`、`extractor.py` | 身份、口味、回复格式、项目规则、排障经验 |
| 情节记忆 | `extractor.py`、`models.py::Episode` | 任务过程、最终决定、事件与关联记忆；S05、S07 是观察样本 |
| 空闲后台抽取 | `MemoryExtractionHook.after_run` 装定时器，`MemoryExtractor.run_idle_extraction` 增量处理 | 默认等最后一轮结束后 120 秒再开始抽取，随后还需要模型调用时间 |
| 信号过滤 | `extractor.py::_has_enough_idle_signal`、`filters.py` | 太短的独立消息可能被跳过；闲聊、AI 自答和一次性产物不应变成用户事实 |
| 自动检索注入 | `gateway_runtime.py` 接 `MemoryStoreAdapter → RetrievalEngine → AgentLoop` | 必须新会话提问；检查实际注入的记忆和最终回答 |
| 多路召回、重排 | `retrieval/engine.py`：语义、情节、近期、附件四路；`reranker.py` 综合相关性、新鲜度、重要性、访问频次 | 同义改写、相似项目干扰、多事实完整性；附件不在本集范围 |
| 搜索后端 | 默认 `memorySearchBackend=fts5`；网关可接可选 Chroma，`store_adapter.py` 做 FTS5 与向量的 RRF 融合 | 第一轮先测默认 FTS5；不能把“语义通道”名称当作必然用了 embedding |
| 更新与冲突合并 | `extractor.py::_merge_into_existing`、`profile_extractor.py::merge_profile_incremental` | 当前值必须用新值；旧值能否回溯另计，不能默认有完整版本历史 |
| 工作区隔离 | `provenance.py::memory_visibility_ids`，会话明确工作区决定归属 | 可见集合为全局＋当前工作区；主集先固定同一归属，隔离另测 |
| 手动查看、编辑、搜索、删除 | `webui/src/components/settings/memory/MemorySection.tsx`、`nanobot/webui/memory_routes.py` | 查看真实落库内容与来源；列表搜索成功不等于自动检索成功 |
| 旧文件记忆与 Dream | `nanobot/agent/memory.py`、`nanobot/agent/context.py`、`DreamConfig` | 可能另从 MEMORY.md / USER.md 等进入上下文，必须记录来源，避免错误归因 |

关键设置位于 `agents.defaults`：`memoryEnabled` 默认 **false**；`memoryIdleSeconds` 默认 **120**；`memorySearchBackend` 默认 **fts5**。WebUI 记忆页的总开关可更新运行时设置。

现有 `tests/memory/manual_memory_test_cases.md` 有“每轮自动整理”“删除会话才出情节”等旧说明；本指南按当前 idle 代码与网关接线设计。**不需要删除历史聊天来完成这次测试**，关闭标签页也不能视为抽取已完成。网关进程须保持运行。

已知边界：画像按 subject＋predicate 合并可能覆盖旧内容，否定冲突可能保留旧内容并记冲突。因此 Q21–Q23 是历史保留挑战，失败可以揭示能力边界；不要为了让系统通过而删掉这些题。

## 3. 图片里的做法怎样适配本项目

图片描述的是“40 题、含 20% 无答案、记录 Recall@k / MRR / 误拒率”的小型评测。它可以作为规模参考；截图中其他人的 0.82 等数字不能作为本项目基线，更不能承诺复现。

普通知识库问答可以主要测“文档能否找回”；聊天记忆还需要测“之前有没有存进去、后来有没有更新、究竟是谁的事实”。本设计因此使用历史会话＋事实证据＋查询三部分。维度参考 LongMemEval 官方基准的信息提取、多会话推理、知识更新、时间推理、未知信息拒答；本集为项目自建练习，**不是 LongMemEval 官方子集，分数不可横向比较**。参考：<https://github.com/xiaowu0162/LongMemEval>。

三种路径比较：

| 路径 | 能回答什么 | 局限 |
| --- | --- | --- |
| **先做 8 题本地聊天体验（推荐起点）** | 能否存、换会话能否答、明显串人串项目吗 | 手工过程会改变记忆，适合诊断，不能当严格可复现基准 |
| 固定记忆快照的离线检索评测 | 哪些事实进了 Top-k、排序怎样、检索延迟多少 | 不直接验证聊天抽取和最终回答；目前需另写适配脚本 |
| 历史对话回放＋隔离实例的端到端评测 | 完整链路以及开关前后收益 | 模型调用多、等待较长，需要自动化准备和快照恢复 |

推荐顺序：8 题体验 → 40 题人工初测并归因 → 如有持续迭代需求，再实现快照评测脚本和回归门禁。

## 4. 标注数据结构与输入方式

`corpus.json` 有 8 段历史会话、26 条用户消息、30 条事实，以及假设、讨论备选、确认和感谢等非事实标注。按 S01 → S08 顺序输入；每段单独建一个聊天。每条用户消息发出后等待真实回复，保存真实 assistant 回复，不预先伪造。

| 会话 | 主题 | 主要验证点 |
| --- | --- | --- |
| S01 | 林澈、前端工程师、编辑器、包管理器、回复偏好、初始杭州 | 身份与偏好 |
| S02 | 用户口味、跑步、同事陈宁的职业与咖啡 | 细节、人物归属 |
| S03 | 青禾库存技术栈、PostgreSQL、旧发布日、审批人、旧上传限制 | 项目事实 |
| S04 | 星港笔记、Python / FastAPI、SQLite、周日发布 | 相似项目干扰 |
| S05 | 发版步骤、白屏原因、实际修复经验 | 顺序、情节与经验 |
| S06 | 搬到苏州、青禾改为周五 19:00、上传改为 50MB | 跨会话更新 |
| S07 | 邮箱密码 → 讨论微信扫码 → 最终不加扫码 | 最终决定 |
| S08 | 上海骑车只是设想、朋友生日、同事房租、寒暄 | 无答案和防污染 |

日期是语料里的逻辑顺序：每条事实更新由用户文本明确声明，不要求真的等到指定日期，也不会自动改变运行时系统时钟。本集不测真实 TTL 到期和长期遗忘速度。

事实 F01–F30 是**人工定义的语义标签**，不是生产数据库里的 memory_id。每轮抽取可能合并、拆分、改写文本；核对时须依据含义与来源建立 `fact_id → 实际 memory_id / episode_id 集合` 的映射。一条记录可支持多个事实，一个事实也可对应多条记录。不要把“必须刚好生成 30 条记忆”设为标准。

历史事实 F14、F16、F24 已被更新；27 条是最终仍有效的事实。写入核对按“当前事实保真”和“历史可回溯”分别记录。

`cases.jsonl` 每行一题：`id / split / category / answerable / query / gold_fact_ids / expected_answer / required_points / failure_conditions / evidence_turn_ids`；无答案题另标出干扰事实。**发给被测模型的只有 query，绝不能把答案、事实表和证据一起贴进去。**

这是功能练习集：不同题会重复考同一事实，40 题不是 40 个独立真实用户样本。8 题 dev 为 Q01、Q04、Q05、Q17、Q25、Q30、Q33、Q40，其余 32 题为保留 test；如果根据 dev 调参，应以未参与调参的 32 题报告后续结果，不把全 40 题包装成盲测成绩。

## 6. 本地怎样启动与体验

### 6.1 推荐入口是聊天网关的 WebUI

可以直接本地启动后聊天。推荐 `nanobot webui` 或已连接本地网关的桌面聊天窗口：当前网关明确装配了这套记忆抽取和检索。不要把“随便调用一个聊天 API”或普通多轮模型脚本等同于这一链路。

使用独立测试配置和工作区，避免与真实用户资料混在一起。以下命令是**供你执行的操作说明，本次尚未执行**；端口若被占用，应换一对空闲端口。

在本仓库根目录运行（当前环境已经有 uv 虚拟环境）：

```bash
uv run --no-sync nanobot webui \
  --config "$HOME/.zhixu-memory-practice/config.json" \
  --workspace "$HOME/.zhixu-memory-practice/workspace" \
  --port 18791 \
  --gateway-port 18790 \
  --yes
```

启动器可创建独立配置并打开页面。在这个实例的“设置 → 模型”中配置可用模型，先确认普通聊天能回复；新配置不会凭空继承你日常实例里的模型凭证。凭证只在本地设置中管理，不写进本数据集或报告。此命令参数来自 `nanobot/cli/webui.py::webui`；没有在本次任务中进行真实启动验证。

首次安装、缺环境时按项目安装文档准备依赖；不要为这套练习额外安装向量模型。默认 FTS5 就能先测。

### 6.2 开测前四项确认

1. 在“设置 → 记忆”启用记忆总开关。默认关闭，普通聊天能回复并不意味着记忆已打开。
2. 主集所有源会话、测试会话使用**相同的实际工作区归属**。项目名“青禾/星港”是题目里的实体，不需要建立两个真实工作区。
3. 在本测试配置中关闭周期 Dream，避免测试途中改变 MEMORY.md / USER.md；确认这些旧文件里没有本集答案。关闭新记忆开关不等于清除了旧文件上下文。
4. 记录模型、preset、温度、后端、idle 秒数。第一轮保留 idle=120；需要缩短可在专用配置中将 `agents.defaults.memoryIdleSeconds` 设为 15 并重启，但不要把 15 秒当生产默认。

### 6.3 先跑 8 题的具体顺序

1. **可选空库基线**：趁测试实例仍为空，关闭新记忆开关，每题新建聊天，依次只问 Q01、Q04、Q05、Q17、Q25、Q30、Q33、Q40。保存答案，不纠正、不报标准答案。预期大多无法知道这些私有事实；这里的“预期”不是已实测结果。
2. 开启记忆。按 `corpus.json` 输入 S01–S08，每段单独新建聊天，每条消息等待回复后再发下一条；一段结束后停止发消息，保持网关运行。
3. 每段至少等 idle 阈值，再等模型抽取完成。打开记忆页核对相关条目和来源会话；有控制台时找 `idle memory extraction finished`，并查看 memories/episodes 的实际计数。只看到定时器触发还不算落库成功，日志完成但计数为 0 也要检查原因。
4. 尤其核对 S06 三个新值“苏州、周五 19:00、50MB”和 S07 最终“不加微信扫码”。没有落库就先标为写入失败，不进入“检索差”的结论。
5. 全部源会话写入后，新建一个空聊天只问 Q01；再建另一个空聊天问 Q04，如此测完这 8 题。**不要切回刚才输入资料的聊天问答案**。每题只发该题 query，不附答案和证据。
6. 记录实际回答、可见记忆、是否串人/串项目，以及有没有文件读取、联网或原始会话搜索等其他取证路径。允许正常记忆检索；如果答案来自其他工具，应单独标记，不能归功于自动记忆召回。
7. 可加一次持久性体验：确定抽取已完成后正常退出网关，用同一配置/工作区重启，再新建聊天问 Q04、Q25。如果仍正确，并能找到存储证据，说明不只是内存中的聊天上下文。

不要通过删除源聊天触发抽取；也不要删除日常记忆。记忆页“手动新增事实”只适合后续单独测检索，不可混进本轮自动写入成绩。

### 6.4 为什么不能立刻把手工 40 题称作严格基准

每个新聊天本身又可能触发 idle 抽取，回答内容也可能影响后续记忆。每题新建聊天能隔离对话上下文，但**不能隔离共享记忆库的变化**。因此顺序问完 40 题可以当人工初测，并记录题序和运行过程，不能宣称完全可复现。

正式端到端比较需要：写入全部历史后正常停止网关，保存独立实例的记忆及会话/配置状态快照；每个条件、每道题都从同一份初始快照派生隔离实例，提问一次后丢弃该派生实例。不要在仍运行的 SQLite 数据库上用简单复制主 db 文件代替一致性快照，WAL 可能尚未合并。

快照中也要固定 MEMORY.md、USER.md、身份配置、模型参数和向量索引（启用向量时）；只恢复 `state.db` 不足以保证整套上下文一致。主结果标注实际日期、新鲜度与访问计数；长时间跨日复跑会改变重排，不宜假设天然确定性。

这套快照回放自动化**本次没有实现**。如果只想先看到效果，先做上面的 8 题即可；要自动跑批再单独实现适配脚本。

## 7. 如何给分与定位问题

### 7.1 人工回答评分

每题记录：题号、模型/设置、实际 session_id、实际回复、支持事实/实际记忆 ID、支持来源、分数、失败层级、备注。

- **2 分**：所有 required_points 都满足，没有触发 failure_conditions。允许同义表达和等价时间格式。
- **1 分**：有部分正确，但缺少关键点；例如只答“拿铁”而丢掉燕麦或无糖，或多事实题只答出一半。无依据编造不能用“部分正确”抵消。
- **0 分**：错误、关键关系颠倒、有依据却明确拒答，或触发任一实质性 failure_conditions。
- 无答案题只给 2 或 0：明确信息未知且无编造得 2；编造具体事实得 0。仅说“我无法透露”不等于知道没有记录，须人工辨别。可以顺带澄清干扰人物，但不要求特定措辞。

报告“严格通过率”时只算 2 分，1 分不算通过；另报部分得分，不能把两者混为一个正确率。否定句和历史说明按语义判定，例如“以前是 20MB，现在是 50MB”在当前值题里不应因出现字符串 20MB 被自动判错。

### 7.2 三层归因

| 观察 | 归因 |
| --- | --- |
| 相关用户事实没有进入语义或情节存储，或实体/数值写错 | 写入/抽取失败 |
| 事实存储正确，但实际注入列表没有覆盖所需事实 | 检索、排序、可见性或预算失败 |
| 实际注入覆盖证据，但回答错、用旧值或串实体 | 回答使用失败 |
| 内容存在 MEMORY.md / USER.md 或来自文件/网页工具 | 标为对应来源；不能直接计作新检索链路成功 |
| 事实不存在，系统明确承认不知道 | 无答案题正确拒答 |
| 输出正确，但没有任何可核查来源 | 答案层可得分，来源标记未知；不反推检索成功 |

记忆页手动搜索使用管理接口，聊天使用 `RetrievalEngine`，二者不同。`相关记忆（自动检索）` 是上下文注入标题，不保证作为最终回复文案显示；模型说“我记得”也不是检索成功证据。

### 7.3 指标与分母

图片中的指标要分清层级，优先同时报告以下几项：

| 指标 | 本集定义 |
| --- | --- |
| 当前事实写入覆盖率 | 抽取结束后完整、正确存下来的当前事实数 / 27；历史 3 条另报 |
| 可回答题严格通过率 | Q01–Q32 中得 2 分的题数 / 32 |
| 无答案正确拒答率 | Q33–Q40 中得 2 分的题数 / 8 |
| 无答案编造率 | 无答案题中给出无依据具体事实的题数 / 8 |
| 误拒率 | 可回答题中明确拒答的题数 / 32；不把所有答错都当拒答 |
| 全集严格通过率 | 得 2 分的题数 / 40；必须同时报上面两类，防止全拒答掩盖问题 |
| 有效记忆收益 | 同题、同设置、同初始状态：启用记忆的通过率减去对照通过率，单位为百分点 |

若只评保留 test，分母相应改为 26 道可回答＋6 道无答案，共 32 道，明确报告 split。

检索层需拿到**真实有序候选/注入 ID**，不能从最终回复臆测 Recall 或 MRR：

- 对自然抽取结果，先建立事实与真实记忆 ID 的对应关系。设题目需要事实集合 G，前 k 条结果完整支持的事实集合为 H，报告 **FactCoverage@k = |G ∩ H| / |G|**，按可回答题宏平均；推荐 k=1、3、5。只有语义相近但缺关键数值或人物归属不算覆盖。
- **MRR@5**：前 5 条中首个真正支持至少一项所需事实的结果在第 r 位，记 1/r；没有则 0，按可回答题平均。它不能说明多事实题已经完整召回，必须搭配 FactCoverage 与最终通过率。
- 若建立的是固定、独立条目的检索集，且完整标好了相关文档 ID，才另报标准 **Recall@k = 前 k 条相关文档数 / 全部相关文档数**。不要把 FactCoverage 与标准文档 Recall 混称同一指标；同一事实的重复记忆也不应重复奖励。
- 原始候选、重排结果、最终注入是不同阶段，报告时标清测哪一层。例如最终注入覆盖不足可能是预算裁剪，不能一律叫召回没命中。
- 无答案题 G 为空，Recall / MRR 记 **N/A**，不纳入这两个指标平均。是否注入无关内容与是否编造分开记录；当前“近期”通道可能召回无直接关键词关系的记忆，不能预设所有无答案题都必须返回空列表。
- 检索延迟统计检索阶段耗时，回答延迟统计从发问到完整回复的耗时，分别报中位数/P95；40 题的延迟仅作小样本观察。

代码入口：`RetrievalEngine.retrieve_with_ids` 返回 `(注入文本, 有序 memory_id 列表)`；`retrieval/trace.py` 有阶段日志，但单段明细有数量和内容截断。正式机器指标应直接捕获完整 ID 和阶段结果，不能只靠截断的日志截图。

建议第一轮只收集真实基线，再设回归门槛。40 题只够探索，不足以证明生产可靠性；无答案共 8 题，错 1 题就是 12.5 个百分点，不宜解读微小差距。

## 8. 现有评测中心能不能直接导入跑

**不能把本数据直接导入后，就声称测到了当前网关的完整长期记忆。**

证据：

1. `nanobot/evaluation/datasets.py` 的 Excel 导入面向普通多轮对话，按同名用例合并 turns，不提供“历史会话写入 → 等 idle → 切新会话 → 冻结共享记忆”的编排。
2. `nanobot/evaluation/fixtures.py::seed_memory` 把种子写入旧 `MEMORY.md`。
3. `nanobot/evaluation/runtime_factory.py` 创建 `AgentLoop.from_config` 时没有传入网关使用的 MemoryServices、RetrievalEngine 与抽取启用参数；它还明确禁用了 Dream 等子系统。

所以现有评测中心更适合普通对话、工具执行、旧文件记忆条件下的回答评测。本次 JSONL 是专用设计格式，**不是已经兼容的导入模板**；将来需要适配回放、快照、工作区、真实检索证据和结果导出，才能纳入批量回归。

## 9. 后续可选扩展，不混入本轮 40 题

- **工作区隔离**：使用同一共享记忆库里的真实工作区 A/B，全局事实可跨区，A 的专属事实不能在 B 注入。两个完全独立实例查不到对方数据，只能证明实例隔离，不能证明共享库工作区过滤。
- **删除效果**：在隔离测试数据里删除目标语义记忆后，检查是否仍有情节、MEMORY.md、USER.md、工作记忆等副本。删一条数据库记录不等于已从所有渠道遗忘；报告“检索撤回”与“全部副本遗忘”的区别。
- **重复与过期**：重复陈述是否制造多条副本；expires_at / superseded_by 对真实检索的影响。
- **同义召回**：在保持语料和查询不变的前提下，对照 FTS5 与已正确同步索引的 Chroma，先确认实际启用和索引覆盖，再比较。
- **更难长历史**：加入更多相似项目、无关历史和更长间隔。这 8 段短历史通过，不等于长周期产品效果已被证明。
